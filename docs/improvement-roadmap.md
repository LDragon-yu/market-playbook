# 见势：项目评估与改进路线（2026-11-04）

## 一、现状评估

这个项目比多数个人交易系统成熟：约 5100 行 Python，分层清楚（sources 适配器 / engines 纯函数 / services 流水线 / SQLite / 原生前端），文档对数据权限、降级策略、LLM 边界、T+1、通知语义都写得很克制。设计上最值得保留的三件事：

1. **确定性规则管门槛，LLM 只做解释**。空仓判定、候选排序、T+1、行情时效都不交给模型，模型动作有白名单，失败自动回退硬规则。这是这个系统最重要的架构决策，后续不要动摇。
2. **失败降级做得很细**。Tushare 各接口失败进 warnings、外围行情缺失时明确提示人工核对而不是编造、监控快照按日期判 stale。
3. **飞书双向通道 + 统一出站接口**，让"电脑端研究、手机端执行"的闭环成立，且出站接口可被其他 agent 复用。

但数据库里的实际使用痕迹说明系统只跑通过一次完整链路：真实复盘停在 2026-09-28（情绪分 29.6「冰点」，涨停 35 / 跌停 62，最高 5 板，建议空仓），有 35 条股票资料、21 条监控项、27 条快照，但 `plan_evaluations`、`monitor_alerts`、`stock_questions` 都是 0 行。也就是说：**信号生产链是通的，但"生成 → 验证 → 修正"的反馈闭环还没有转起来**。测试基线不错（37 passed, 1 skipped），但引擎层只有 2 个用例。

下面按优先级给出改进方向。核心判断是：现阶段缺的不是功能数量，而是反馈闭环、情绪指标的专业度、预案的可执行性这三件事。

## 二、P0：先修闭环（约一周）

### 1. 让评估结果真正回到产品里

`app/services/pipeline.py:162` 把 `evaluation` 硬编码成了 `None`，而 `plan_evaluations` 表其实在每天盘后任务里会写入（`pipeline.py:76-77`），前端和飞书都看不到。同时 `app/engines/validation.py` 只统计候选的"收盘是否上涨"，维度太窄。

建议把验证扩展为四层：情景命中（高开/低开/平开与实际走势）、候选开盘买入持有至收盘/次日的收益、MFE/MAE（从开盘的最高/最低偏离，现在算了但没进统计）、以及**空仓建议的有效性**（建议空仓的次日市场涨跌）。另外补上板块判断的验证（判为"主线"的板块次日是否延续）。然后在前端加一张"昨日预案验证"卡片，飞书日报末尾附一句结论。没有这层，权重只能拍脑袋。

### 2. "冻结"目前只是字样，不是约束

`app/db.py:117` 的 `save_plan` 用 `ON CONFLICT ... status='frozen'` 覆盖写入——同一天重复运行盘前任务会静默改写已经冻结的预案，和文档承诺的"收盘只做验证，不做事后改写"矛盾。建议：盘中（9:15 之后）禁止覆盖当日预案；确需修改时写入新版本并标记旧版 `superseded`，保留改写痕迹；`plan` 里记录生成时的输入哈希（复盘日期、情报 id 列表），便于事后审计。

### 3. 候选池必须"可买"

`app/engines/review.py:78` 已经算出了 `is_one_word`（一字板），但全项目没有任何地方读取它。一字板排板和 ST、上市不足 60 日的次新股，会以高分进入候选池或抬高市场高度。另外 20cm 板（创业板/科创板）的涨幅在评分里天然占优：`min(15, pct) * 1.2` 让 20% 的票比 10% 的票多拿 6 分。建议在 `_stocks`（`review.py:297`）里统一做可买性过滤与板别归一化，候选卡片标注"仅观察（一字/ST/次新）"而不是直接剔除，保留信息但不误导执行。

### 4. 按日存储全量涨停宇宙

`review.py:165` 把 `stocks` 截断到前 40 只后存 JSON。这导致后续想算"昨日涨停今日溢价""连板晋级率"，以及做回测时，历史数据不够用。建议新增 `limit_up_daily`、`sector_daily` 两张结构化日表，存全量涨停/炸板/跌停个股、板块成员与强度快照。这是后面所有分析的地基，越早建越好，历史可以先用 Tushare 回补 1-2 年。

### 5. SQLite 并发与数据保留

`app/db.py:64` 的 `connect()` 没有设置 `busy_timeout`。目前飞书子进程、监控线程、cron 任务、Web 请求会同时写库，出现 "database is locked" 只是时间问题。加 `PRAGMA busy_timeout=5000`，并给定时任务加一个与 `worker_lock.py` 同机制的进程锁，防止 cron 和手动触发同时跑盘后任务。

快照表 `market_snapshots` 每天约 18 只 × 240 分钟 ≈ 4300 行且永不清理；告警、决策、问答表同样只增不减。建议快照保留 30 天、告警 90 天，启动或每天盘后做一次清理，季度 VACUUM。

### 6. 版本管理与依赖一致性

目录不是 git 仓库，`.env` 里有真实 token，本地 `__pycache__` 是 Python 3.14 的字节码，Docker 用 3.12，`pyproject.toml` 写 `>=3.11`，版本号还有 0.1.0（pyproject）和 0.3.0（main.py）两个——建议立即 `git init`（确认 `.gitignore` 已覆盖 `.env`、`data/*.db`）、加 GitHub Actions（ruff + pyright + pytest）、用 uv 或 pip-tools 锁定依赖、统一 Python 版本与版本号。顺便把 `data/market_review.db` 从工作目录移到不会被云盘同步的位置备份，`.env` 同理。

## 三、P1：交易逻辑升级（2-4 周，真正的价值所在）

### 1. 情绪体系补全（优先级最高）

现在的 `emotion_score` 是广度、涨跌停差、连板高度、指数的静态加权（`review.py:98-105`），作为 v0 是合理的，但缺了 A 股短线最核心的四个指标：

- **涨停溢价**：昨日涨停股今日平均涨幅——这是判断赚钱效应最直接的指标；
- **连板晋级率**（n 板 → n+1 板）与**首板晋级率**；
- **封板率**：涨停 /（涨停 + 炸板），比现在的炸板率更常用；
- **大跌家数**（跌幅超过 5% 的家数）与跌停结构。

建议把"指标层"和"状态层"分开：每日计算指标并入库，状态由指标的历史分位（如 250 日）和趋势共同决定，输出"周期位置"（启动/发酵/高潮/分歧/退潮）而不只是一个档位。这样也自然解决了冰点/退潮阈值写死（32/43/55/66/80）的问题——阈值应该随市场环境校准，而不是常数。

### 2. 板块强度重构

`review.py:209` 的板块评分是 `42 + pct*4 + up_count*3 + high_count*4 + days*2 - rank`，各项量纲不通，大板块容易垄断前几名（9 月 28 日"一带一路"84.3 分的例子）。建议改为成员级计算：扩散度（板块涨停家数/成员数）、龙头高度、梯队完整性（是否有首板、二板、三板梯队）、连续活跃天数、资金净流入，各自归一化后加权；输出"板块梯队结构"而不只是单一分数。数据上用 `ths_index` + `ths_member` 批量构建板块成员表，而不是现在按个股逐个查（`classification.py:58-77` 每股 3 次请求、串行，40 只股票会很慢）。

### 3. 盘前预案可执行化

`plan.py:93` 的"高开约 2%～5%"是定性区间，盘中无法直接对照。建议每个候选生成具体价位：昨收、涨停价、合理高开价上下限（元）、盘中失效价（如跌破昨收或分时均价）、板块龙头的对照阈值。更进一步：**9:25 集合竞价结束后自动核对门槛**——用 `rt_k` 的竞价开盘价和板块龙头表现，生成一条 `gate_check` 记录（通过 / 不通过 / 观察），标注在预案上但绝不改写预案。这一步把系统从"参谋"变成"执行辅助"，而且是现有数据管线就能做到的。

情报权重也值得改：`plan.py:31` 目前按正负条数差 ×2 封顶 ±10，与信息和候选是否相关无关。建议按"与候选板块的相关性 × 来源可信度 × 时间衰减"加权，只在候选所属板块有情报时计入。

### 4. 回测与事件研究

有了全量日表后，写一个 `scripts/backtest.py`，用 Tushare 历史数据重放 1-2 年：按 regime 统计候选次日收益分布、空仓建议的规避效果、板块"主线"判断的持续性、不同情景（高开/低开/平开）的条件收益。目标是给出"在发酵期做首板、次日平均收益 X%、胜率 Y%"这类可校准的数字，然后用它调整权重。这是让系统从"逻辑自洽"变成"有据可依"的唯一路径，也是和普通复盘工具拉开差距的地方。

### 5. 交易日志与执行偏差

持仓表有了 thesis/invalidation，但没有实际成交记录。建议加 `trade_executions` 表（成交价、时间、理由、对应哪个预案候选），统计胜率、盈亏比，以及最重要的**纪律分**：有没有做计划外的票、有没有在失效条件出现后继续持有、实际仓位有没有超过上限。对短线系统，行为层面的改进往往比信号本身更值钱。

### 6. 仓位管理

目前只有一个总仓位上限 `max_exposure_pct`。建议增加账户净值设置和单票风险预算：例如单笔止损 -3%、账户风险 1%，则股数 = 净值 × 1% ÷ 3%；再加板块集中度上限（如单板块不超过总仓位 50%）。这些规则可以完全确定性实现，不涉及模型。

## 四、P1-P2：盘中监控

`rt_k` 单股串行请求（`portfolio_service.py:148,258`）是当前最大的体验瓶颈：18 只一轮 20-60 秒，60 秒间隔下实际频率可能只有约一分钟一次且会漂移，急跌时提醒会慢。建议引入批量快照（如 AKShare 东财全市场 spot 接口）作为主源，`rt_k` 降级为单股确认；持仓股优先，其余按优先级轮询。同时把告警阈值按角色/板别/时段配置化，并加升级机制（回撤 -4% 警告 → -7% 危险、封板打开次数），14:30-14:57 单独一组尾盘规则。

另外两处小问题：行情新鲜度目前用日期字符串比较（`portfolio_service.py:155`），建议解析时间戳计算秒级 staleness（超过 5 分钟即作废）；`monitor_worker.py:61` 要求当天盘前预案已生成才启动监控，如果盘前任务失败，盘中就完全失明——建议回退到用最新复盘直接构建 watchlist。

## 五、工程与运维

- **日志**：现在错误分散在 job_runs 和 warnings 里，没有统一的日志文件。建议标准 `logging` + `data/logs` 轮转文件，关键路径带 job_id 和 ts_code。
- **迁移**：schema 靠 `CREATE TABLE IF NOT EXISTS`，加字段时无路可走。加一个 `schema_version` 表 + 顺序 SQL 脚本即可，不需要 Alembic。
- **配置**：`Settings` 在 import 时读环境变量，热更新靠 `pipeline.__init__` 重新初始化（`main.py:32`），能用但脆弱。可以逐步换成 pydantic-settings，但优先级不高。
- **Docker**：加非 root 用户、HEALTHCHECK、固定基础镜像；生产环境 Basic Auth 前面用 Caddy/Nginx 做限流，写接口（情报解析、个股问答）加简单的每分钟限流，防止误刷 LLM/OCR 成本。
- **LLM**：输出目前只 `json.loads`，建议用 pydantic 校验字段并加一次修复重试；对文章内容做注入隔离（明确分隔符 + "忽略文中指令"）；记录 token/延迟/成本，按文本哈希缓存摘要。
- **测试**：在现有 37 个用例基础上，补引擎的 golden fixture（固定输入 → 固定输出）、FastAPI TestClient 的接口测试、以及 Tushare 响应的录制回放，重点覆盖降级路径（接口失败、字段缺失、数据不完整）。

## 六、产品体验

数据都已在库里，只差呈现：情绪分 30 日曲线与涨跌停趋势（复盘按日存储，直接画）、候选评分的分项拆解（现在只有总分，无法解释为什么是 75 分）、复盘/预案的历史对比、每周五的飞书周报（本周 regime 分布、候选命中率、纪律分）。移动端已由飞书覆盖，不必再做 PWA。

## 七、建议路线图

第 1 周：P0 六项（评估回填、冻结约束、可买性过滤、全量日表、并发与保留、git + CI）。

第 2-3 周：情绪指标补全、板块强度 v2、9:25 竞价门槛核对。

第 4-6 周：回测框架与权重校准、交易日志与纪律分、仓位管理、批量行情源。

之后：LLM 稳健性、日志与运维、前端可视化、飞书周报。

---

## 八、明确不建议做的事

不接券商自动交易——合规风险和操作风险都不值得，当前"不自动下单"本身就是产品优势。不要为这个规模上 Postgres、消息队列或微服务，单用户 SQLite 完全够用。不要追求全市场 tick/Level-2，现有数据代理不支持，性价比也低。不要让 LLM 参与权重调参或绕过任何门槛——规则保持确定性，用回测结果人工校准，LLM 只做解释和情报结构化。

---

## 九、总体判断

值得继续做，而且底子比大多数同类项目好。它现在的问题不是"功能不够"，而是三条主线还没走完：**评估没有回到界面（反馈闭环断）、情绪指标不够专业（信号质量有上限）、预案停留在文字（无法执行对照）**。把 P0 和情绪指标这两块补上，这个系统就会从"每天生成一份报告"变成"每天可以验证和改进的交易纪律工具"，后者才是它能长期活下来的理由。
